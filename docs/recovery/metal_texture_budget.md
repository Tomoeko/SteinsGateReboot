# Metal texture admission policy

The original BasicPicture script loads the next image before clearing its current picture (`basicpicture.nut` loadImage PCs 804–812). The actual gameplay replay reaches this overlap for `image/resg_bg008a1.psb`: 265,095,168 registered texture bytes plus two valid BC7 sources expanded to 50,331,648 RGBA bytes. The complete upload needs 315,426,816 bytes, above the previous authored 256 MiB ceiling. This is a port admission limit, not an original file-format or native D3D limit. Early picture retirement would change the recovered script order.

`SpritePassDescription::MaxTextureBytes` retains its positive default and explicit limits. Zero opts into the selected Metal device's `recommendedMaxWorkingSetSize`, resolved once at renderer creation and checked for positive, representable size. Shared targets inherit that resolved ceiling when requesting zero; conflicting positive limits reject. `Description()` returns the effective positive value. The game host explicitly requests this policy and passes the same effective byte and texture-count limits into its common image/motion/font preparation cache. Individual texture decoding retains its separate 64 MiB bound.

Apple describes the recommendation as approximate memory guidance for performance. It is neither available memory nor an allocation guarantee. Actual Metal allocation failures and bounded arithmetic still reject. No queries or policy changes occur in ordinary frames. See [Apple's device recommendation](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize).

The source and private diagnostic overlay pass strict compilation and independent review. The bounded receiving fixture uses two one-pixel A8 atlases, shared-target pixel checks, explicit-limit rejection and retirement/reuse; all 642 coherent public tests, the private host build and the independently linked private GPU fixture pass. Evidence is retained under `Files/research/runtime/metal-device-texture-budget-stage/` and `gameplay-background-texture-footprint-stage/`.

The immutable Metal path now offers an optional original-block BC7 service when the selected device supports it. The existing first-party RGBA decoder remains the fallback when that capability is absent; an actual compressed upload error propagates. Stored dimensions, exact ranges, positive block-row stride and the existing decoded-extent limit remain checked. The synchronous upload borrows source blocks only until return, charges stored bytes and reports physical DXGI 98 only for actual compressed GPU storage.

All 769 supplied image resources and 1,364 texture wrappers pass actual Metal creation/upload/release, post-purge selections, exact source-block digests and ordered final retirement: 1,178 compressed BC7 sources and 186 A8/L8 sources. Peak logical live upload charge is 16,785,408 bytes. Independent tiny GPU probes match bare BC7 decode pixels; the connected sampling fixture explicitly selects the native unmodulated path. These checks do not establish corpus pixels, native Direct3D equality, physical residency or long-play performance. Private gameplay attribution retains the previous RGBA renderer until its separate Emote failure is resolved.
