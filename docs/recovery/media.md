# Movie and media recovery

Target executable: `Files/STEINS.GATE.REBOOT/sgre_steam.exe`, SHA-256 `75a83a0e2a7e22055417ae0474b47be98418c4e42c695c548b558705c404b9d8`. Resource identities are recorded in `resources.md`. Keep plaintext media and the recovered seed under ignored `Files/`.

## Movie transform and container

The extension is supported by actual decoded bytes: all 85 movies contain WebM/Matroska with VP9 video; 25 additionally contain Opus audio. Their byte-zero transform uses MD5 of the original seed followed by the normalized basename, four little-endian seed words, MT19937 `init_by_array`, little-endian output words, and a repeating 4,096-byte XOR key. There is no clear MZS header on these movies.

Executable evidence: `MkvFileReader` construction at `0x1400f5800` calls initialization `0x1400f5d20`; initialization calls key generation `0x1400f5890` with `0x1000` bytes. Basename extraction and ASCII uppercase folding are at `0x1400f6180`, the separate movie MD5 implementation at `0x1400f65e0`, and the bounded read/XOR operation at `0x1400f6050` phases its key from the current file position modulo `0x1000`. This independently corroborates the observed transform. Continuous MT output only decodes the first key period and corrupts later packets; it is not the movie format.

The authored `WebmReader` reads bounded element headers and individual packet payloads from the original encrypted file. It retains track metadata, signed cluster-relative timestamps, nanosecond scales, codec private data, default duration, codec delay, seek pre-roll, lacing, block duration, references, discard padding, and block additions. It rejects unsupported content encodings and non-unit track timestamp scaling. It does not substitute a default frame rate for missing timing. Container rules follow [RFC 9559](https://www.rfc-editor.org/rfc/rfc9559.html) and the [WebM container guidelines](https://www.webmproject.org/docs/container/).

A complete streamed corpus scan processed 286,513 packets/frames and 3,735,679,868 encoded payload bytes without retaining plaintext movies. All packets in this supplied corpus contain a single frame. Synthetic tests separately cover all three lacing modes, unknown cluster length, block additions, signed timestamps/discard padding, rewind, encrypted chunk offsets, malformed sizes, truncation, and allocation/work limits.

## macOS VP9 decoding

The first-party macOS boundary uses public CoreMedia/VideoToolbox APIs, not a linked external decoder. Calling `VTRegisterSupplementalVideoDecoderIfAvailable(kCMVideoCodecType_VP9)` is necessary on this host: the initial hardware-support query returned false before registration and true afterward. Session creation and actual original-frame decoding both succeed. The portable interface contains only owned NV12 pixels, dimensions, timestamps, range, and color-matrix identity; no Apple handles escape it. Call decoding from a worker rather than ordinary rendering frames.

Validation on the current Apple Silicon host decoded the first ten video frames from every movie: 850 frames across all 85 files, each 1920×1080. One complete 15-second sample decoded all 450 video frames. Its zero-based frame 99 has timestamp 3,300,000,000 ns, limited range and the BT.709 attachment. Tight NV12 bytes are identical to independent FFmpeg software output: 3,110,400 bytes, SHA-256 `ff7eb0a7fa2dbcb758df74a2f85124d85cd956c999c7d397e8f978e0ece090cf`. This is one pixel comparison, not all-frame or native-rendering parity.

An independently encoded synthetic 64×64 VP9 black frame verifies exact limited-range luma 16, chroma 128, owned planes, timestamps, drain, and bounds under sanitizers. This host rejected 16×16 and 32×32 session descriptions with OSStatus -12911; 64×64 and larger probes succeeded. Do not infer support for other hardware, profiles, bit depths, or alpha composition from these checks.

## Opus packet and platform research

The first-party Opus identification/framing reader follows [RFC 7845](https://www.rfc-editor.org/rfc/rfc7845.html) and [RFC 6716](https://datatracker.ietf.org/doc/html/rfc6716). It checks mono/stereo mapping-zero headers, pre-skip, original-rate metadata, signed gain, all four packing codes, variable/equal frame lengths, padding, 1,275-byte frame bounds, and the 120 ms packet limit. A complete movie scan accepts all 162,898 original Opus packets; each contains 960 decoded-sample time units at 48 kHz. All 25 identification headers declare pre-skip 312.

An ignored CPU-only AudioConverter probe confirms that original packets produce nonzero float audio without opening an output device. It also exposes priming and numerical differences that must be preserved as acceptance issues. For the first 400 packets of one original movie, AudioConverter returns 383,880 frames; independent software decoding after identification pre-skip returns 383,688. Removing an additional 192 frames aligns the measured outputs (312 declared pre-skip less 120 apparent platform priming). Maximum float difference is 0.00022375956 and RMS difference 0.000004189112; output is not bit-identical. These observations do not establish the original game's Opus output or authorize a guessed fixed timing offset in the engine.

Passing a zero-packet successful callback ends the AudioConverter stream; it must not be used to signal temporary packet starvation. A distinct callback status preserves streaming state in the research probe. Original media timing, priming across seek/reset, gain, final discard padding, and a measured platform adaptation remain open before this decoder becomes an authored runtime service. No probe sends sound to speakers.

## Sound resources and first-party wave decoding

`ReadSoundArchive` validates every data-bearing PSB object in both complete audio bodies: 15,147 entries/channels across 15,142 sound-archive objects, plus five index/group objects. The original formats comprise 83 PCM channels, 45 Microsoft ADPCM channels, and 15,019 WMA Standard channels; no WMA Professional channel is observed. All WMA packet tables agree with encoded length and block alignment. There are 122 channel sample-loop ranges. Preserve exact rates: several original effect headers deliberately differ slightly from 48,000 Hz.

Native playback at `0x1403921a0` recognizes format tags 1, 2, 0x161, and 0x162. It passes `fmt` directly to source-voice creation, `data` to the audio buffer, and WMA `dpds` to the decoded-packet cumulative-byte descriptor. Optional channel `loop` values populate sample begin and length; Microsoft ADPCM loops are rounded down to `wSamplesPerBlock` boundaries. The call's repeat-count mapping remains part of scheduling recovery. This interpretation agrees with Microsoft's [xWMA buffer documentation](https://learn.microsoft.com/en-us/windows/win32/api/xaudio2/ns-xaudio2-xaudio2_buffer_wma).

The authored portable wave decoder handles PCM 8/16/24/32-bit integer samples and Microsoft ADPCM prediction, block headers, interleaving, adaptation, saturation, and checked output limits. A streamed corpus check decoded all 128 supplied PCM/ADPCM channels and processed 524,507,283 interleaved samples transiently. Long clips exceed the convenience function's default 64 MiB output limit; decode aligned blocks on a worker or explicitly set a bounded offline limit. The research scan used at most 192 MiB decoded audio for one clip and retained no full decoded corpus.

One complete original ADPCM clip at sound-body PSB offset 5,643,830 contains 6,161,192 encoded bytes and produces 12,040,192 normalized float samples. Output is byte-identical to independent FFmpeg decoding: SHA-256 `b756d75993b61bc17507a103b0b2653848edea65da4a8580d460e0a91f86e687`. The two 48 MiB comparison outputs were pruned after verification; retain the compact report and bounded encoded comparison input. Codec-block facts and supported XAudio behavior follow Microsoft's [ADPCM overview](https://learn.microsoft.com/en-us/windows/win32/xaudio2/adpcm-overview) and [wave format notes](https://github.com/microsoft/DirectXTK/wiki/Wave-Formats). Original Windows output/resampling and all-clip numerical parity remain open.

A bounded voice sample's three PSB streams can be packaged as research RIFF xWMA and independently decode as WMA v2; its 18-byte `fmt` has no extension. This confirms compressed voice content exists. The first-party WMA algorithm is still unimplemented and fails explicitly. CrossOver's observed XAudio2_8 path is relevant: Microsoft states that version 2.8 lacks xWMA decoding, while 2.7/2.9 support it. Native DLL selection and actual voice-creation HRESULTs still need observation before attributing the compatibility failure definitively.

## Remaining acceptance

Implement and validate Opus movie audio, first-party WMA sound/voice decoding, loop/cue semantics, portable audio/movie scheduling, seek/skip/end behavior, alpha/addition composition, and the actual game's movie-layer renderer. The current AudioToolbox decode-format inventory exposes Opus but no WMA format; a positive format identifier is not evidence that the original packet/cookie layout works. The native Windows movie process at `0x14038f080` uses 10,000,000 clock units per second in its Media Foundation path; the separate WebM path and actual scheduling still need full recovery and retained reference traces. CrossOver captures and one independent decoder comparison do not replace that acceptance.
