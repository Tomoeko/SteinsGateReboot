# Selected motion packets into Metal

The frame receiver joins the populated [selected ordinary sprite owner](motion_selected_sprite_player.md) and its actual shared draw context to `SpritePassRenderer`. The scene owner supplies selection, local/root evaluation, source identity, geometry, persistent row ordering, clipping decisions and measured frame events. This boundary consumes them and copies each transient packet into bounded preallocated vertex/index/draw storage before the borrowed sink returns. It submits one physical Metal pass at the actual End callback, inside the context Flush transaction. A backend rejection propagates before queued rows and their borrows are consumed, permitting a retry after the cause is repaired. An empty context emits no Begin/End; the receiver then performs only the explicit caller-requested target Clear or Preserve operation.

The actual renderer, TextureCache, registered resources, selected player and context must remain live and unchanged through reception. Texture preparation snapshots the same cache-scoped handle, backend texture, original format/dimensions, filtering and address revision. It prepares the measured pipeline variants outside ordinary frames. Later stale resources or changed filters/addresses require preparation again before the queue is consumed. Binding removal retires only the receiver's borrowed identity; it adds no source, texture or self pin. Renderer uploads copy packet storage before return, so later CPU frame preparation cannot overwrite an in-flight GPU upload slot.

`SpritePassDraw::Scissor` carries an optional integer rectangle in physical target pixels. No value restores the complete attachment for that draw. Empty extents suppress its draw while retaining the correct vertex/index/constant offsets for later draws. The Metal backend rejects rectangles outside its actual attachment before command creation. These constraints follow [Apple's scissor API](https://developer.apple.com/documentation/metal/mtlrendercommandencoder/setscissorrect(_:)) and [scissor rectangle fields](https://developer.apple.com/documentation/metal/mtlscissorrect). Native Direct3D rectangles use their recovered signed device bounds; the receiver intersects those bounds with the attachment. That intersection is a platform mapping inferred from fragment/attachment clipping, not a new native GPU observation. [Direct3D's scissor API](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-rssetscissorrects) documents the corresponding state.

The initial applied integer device scissor is an explicit input separate from the prepared frame's rounded CPU cache. [Retained native scissor behavior](motion_scissor.md) proves those states can differ: raw1.9 submits device1 while caching2, and a later raw2.1 request can be cache-suppressed. Device-submission events update the unclamped device state; a cache-suppressed event leaves it unchanged. The result returns the final actual device rectangle with its GPU submission identity, permitting the containing driver to retain that state across frames. Attachment intersection applies only to the copied Metal draw rectangle. Each emitted batch captures its own scissor before the frame's final restore. Shader projection registers are explicit actual driver inputs. No window, display scale, camera matrix, timing or replacement scene is guessed by this receiver.
