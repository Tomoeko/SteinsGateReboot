# Drawable capacity and the frame host heap

Original target: `Files/STEINS.GATE.REBOOT/sgre_steam.exe`, SHA-256 `75a83a0e2a7e22055417ae0474b47be98418c4e42c695c548b558705c404b9d8`.

The native onscreen constructor `4c34a0` configures `DXGI_SWAP_CHAIN_DESC1.BufferCount = 2`. The containing Display factory later calls the actual swapchain `GetDesc` at `4c47c2` and reads the resulting old descriptor's `BufferCount` at offset `0x28`. Pool constructor `54c5e0` passes that output to its real embedded heap `54c110`, alongside kind 5, mode 1 and the 65,536-byte host-page unit. The configured literal alone does not represent that owner/query chain.

`SpritePresentationDescription.BufferCount` supplies the recovered configuration to the actual hidden macOS layer. Its default is two. The existing two-argument diagnostic constructor retains its three-drawable policy. Both configure the real `CAMetalLayer.maximumDrawableCount`, read it back before publication and retain that actual configuration for later validation. The public `DrawableCapacity()` getter checks the same hidden window/view/layer, device, geometry and actual weak renderer receiver before returning the live property value. The receiver must be alive and encoding idle; it need not have an initialized target or a submission. It retains no renderer or target through a new owner.

This is a scoped macOS configure/query translation. Apple defines the property as the drawable resource-pool count. It does not identify an allocated texture, a host-frame index or an available drawable; actual acquisition may wait or return nil. The SDK accepts two or three. [CAMetalLayer](https://developer.apple.com/documentation/QuartzCore/CAMetalLayer), [nextDrawable](https://developer.apple.com/documentation/quartzcore/cametallayer/nextdrawable%28%29?changes=_2_2&language=objc).

The actual readback can initialize `FrameHostHeap`. Pool entry byte zero/one is preserved as an observed CPU state: native Begin `54bec0` clears it through `4c6d20`, then retires the selected frame's pages; End `54c040` sets it through `4c4860`. These helpers perform no GPU wait or upload. This supplied pool's vtable `6547f0 + 0x58` calls `04b570`, returning false, and its ordinary `5313f0 -> 531ed0/531b70/531550` path copies host input through real buffer creation/binding/draw calls. General true-query GPU-entry registration remains outside this lane.

The existing Metal encoder synchronously copies genuine `SpriteHostInputs` into its owned upload buffers. Those buffers remain fenced by their actual command state. The layer capacity leaves the three software transfer slots and three renderer upload slots intact; it is not their reuse condition. Resource-retaining command buffers retain Metal resources, not borrowed first-party CPU page spans. [Resource retention](https://developer.apple.com/documentation/metal/mtlcommandbufferdescriptor/retainedreferences?changes=_3%2C_3).

The scoped fixture constructs its host heap from the actual getter, joins an actual worker's host writes, copies through the ordinary encoder and recycles the host pages before checking independent red target pixels. It makes no drawable request or Present call. It also checks uninitialized-source queries, two/three policy preservation, invalid configuration, changed layer properties, wrong-thread access, live-encoding rejection and expired renderer lifetime. Framework exceptions use the existing first-cause presentation boundary; new foreign exception outcomes are not claimed.

A full containing frame owner still must prevent every host recycle while a writer or synchronous copy borrows its pages, including error and retirement paths. Current Looper success order supplies Pre -> Update -> worker join -> Draw -> Post, but an Update failure after queuing work and before the join is a separate prerequisite. Actual root/Layer/current backsurface production, Display pre/post resource ownership, general GPU-entry registration, native timing and displayed fidelity remain open. This leaf does not enable application-pump Present or original startup.
