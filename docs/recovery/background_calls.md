# Concrete background call ownership

Reference: `Files/STEINS.GATE.REBOOT/sgre_steam.exe`, SHA-256 `75a83a0e2a7e22055417ae0474b47be98418c4e42c695c548b558705c404b9d8`. Native facts below come from readonly Binary Ninja `candidate:view:1:UEU` / `view:1` static analysis. No new native execution or undefined-lifetime probe was performed.

`MFileReadTask` constructor `0x1404d3750` owns embedded MProcess groups, initializes continuous byte `+0x108` to zero and background lane DWORD `+0xcc` to 2, then selects phase `0x1404d6f10`. Ordinary ResourceManager construction sets `+0x108 = 1` through `0x1404d77e0`, installs an owner-borrowing ResourceManagerFileReadTaskSorter through `0x1404d4370`, and appends the real processor into its embedded parallel group. The sorter prioritizes positive signed loading-map reference counts and keeps equal-group order, but read loop `0x1404d43d0` invokes it only when byte `+0x108` is zero (`0x1404d4458`). Installing that comparator is not evidence that the persistent ResourceManager queue should be sorted unconditionally.

The task phase checks mounts and pending queue work. With direct-execution byte `+0x173` false it creates a real `MBgCallTask0<MFileReadTask>` and appends it to embedded serial `+0x28`; otherwise it executes the read loop directly. The background call stores the actual processor pointer at `+0x58` and function pointer at `+0x60`. Virtual `onProcess` `0x140076d40` loads the former and tail-jumps to the latter. Its Draw slot is native empty `0x140030f20`; it is not a renderer producer.

`BackgroundCallTask` and `BackgroundCallManager` recover the concrete job/manager boundary:

- MBgTask Update `0x1404fbf70` appends the actual job pointer once to one of four manager FIFO lists indexed by DWORD `+0x50`. It publishes byte `+0x54 = 1` after queue insertion and does not wake an idle worker.
- The actual post-loop hook `0x1404fbf30` signals only managers whose lists are nonempty. A worker already running drains newly queued work without requiring another wake.
- Worker `0x1404fbde0` removes the head under manager lock `+0x38` and acquires the selected job lock `+0x28` before releasing the manager lock. It invokes job virtual `+0x30`, writes status 2, then releases the job lock.
- Background call destruction `0x1404d3c40` calls `0x1404fbe90` before destroying the job lock/base. That helper unlinks a still-queued pointer under the manager lock, then acquires the job lock and sets byte `+0x55 = 1`. Acquiring that lock waits for a callback already running. It does not interrupt a selected callback.

The portable manager owns four separate threads and actual pointer lists; each nonmoving task has its own lock, required Execute and atomic status. Queue membership adds no task or script root. Close removes a queued pointer or waits for the selected job lock before releasing Execute's captured or borrowed owners. Worker exceptions are retained and reported by explicit Close only after retirement; destructor suppression applies only after retirement completed. A destructor with an unsupported live-owner/self-cleanup condition terminates rather than leave a worker with a dangling pointer.

Ownership mutation, Update, PostLoop and cleanup require the actual creating owner thread. This authored stable-domain rule rejects worker self/foreign-thread cleanup before list mutation. The live-task count is only a destructor preflight; it is not an independent task/receiver registry. Manager shutdown requires all tasks retired. Real Execute owners must enclose task retirement, and containing graph cleanup must run its corresponding owner preflight before dropping any parent resources. The separate [actual file-read serial attachment](file_read_serial.md) now couples the exclusive job to its genuine processor groups, with concrete release preflights and an explicit forced-retirement worker fence. Full resolver/read/decoder/publication services remain required.

Thread startup waits until workers enter their idle loop so initialized-idle wake behavior is deterministic. That barrier, bounded job counts, standard C++ thread shutdown/join, atomic publication, exception reporting and owner-thread cleanup are authored safety/host policies. Original four Windows priorities are not mapped to portable OS scheduling by this source. Native first-worker startup races, process-lifetime worker shutdown, cross-thread graph finalization and all arbitrary callbacks remain unverified.

The ordinary read loop still needs genuine resolver/disk/decoder/publication services. Native queue requests own three filename strings and borrow destination/status cells; success writes output ownership before status 1, raw/read failure writes status 2, and a postprocessing failure branch writes status 4. ResourceManager advances completed loading entries in onProcess before updating the child processor. Queued/raw/PSB cancellation and typed producer ownership must be established before connecting those cells to ResourceCache. `PsbResourceJobs` remains unchanged: its immediate Queue wake and publication flow are not substituted for this native post-loop protocol. MFileReadTask and MDiskFileReadTask teardown delete derived synchronization/file state before the later generic serial destruction; safe native pre-retirement or required quiescence is still an open integration condition.
