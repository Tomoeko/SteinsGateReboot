# Resource vector font tables

Evidence date: 2026-10-12. Original `sgre_steam.exe` SHA-256 is `75a83a0e2a7e22055417ae0474b47be98418c4e42c695c548b558705c404b9d8`. Native `0x1400878a0` opens face index zero and selects the first map whose platform/encoding is `(0,3)` or `(3,1)`. This policy is executable-derived; the table algorithms below follow primary format references. Original bytes and Binary Ninja metadata remained unchanged.

`SfntFont` borrows immutable decoded resource bytes. It reads big-endian fields explicitly, checks directory/tag/range/count invariants, and retains original table and character-map order. It supports the supplied standalone TrueType and CFF sfnt signatures. Collections, variable fonts, and a missing native-preferred map are explicit errors. It does not infer an OS-selected map or substitute a different face. Table and whole-font checksums can be checked during preparation. Directory and checksum rules follow the [OpenType font-file specification](https://learn.microsoft.com/en-us/typography/opentype/spec/otff).

Character mapping implements format 4 delta/glyph-array segments and format 12 coverage groups. It validates ordered, nonoverlapping coverage and every mapped glyph against `maxp`, including format 4's terminal segment and relative glyph-array offsets. Lookup uses binary search without allocation. Metadata for other observed maps, including Macintosh formats 2/6 and variation format 14, is retained; requesting their mapping operation fails explicitly. The selected BMP map does not gain supplementary coverage merely because the font also has a format 12 map. These rules follow the [OpenType cmap specification](https://learn.microsoft.com/en-us/typography/opentype/spec/cmap).

Horizontal and vertical metric readers preserve integer advances and signed side bearings, including the tail whose advance repeats the final full metric. They use counts from the matching headers and `maxp`. Missing vertical tables return no metrics; vertical-origin synthesis, VORG use, hinting, and pixel-size scaling are separate behavior. Format references are the [horizontal metrics](https://learn.microsoft.com/en-us/typography/opentype/spec/hmtx), [vertical metrics](https://learn.microsoft.com/en-us/typography/opentype/spec/vmtx), [font header](https://learn.microsoft.com/en-us/typography/opentype/spec/head), and [maximum profile](https://learn.microsoft.com/en-us/typography/opentype/spec/maxp) specifications.

## Native owner observation and unhinted advance scaling

A separately guarded initialized-game probe constructed private vector-font owners from the retained `SourceHanSansTC` OTF, modes 0/3/4 and language `en`, then measured twelve UTF-16 units at integral sizes 12/24/48. The source font remained 16,522,392 bytes, SHA-256 `44af35f7ecf9947a02ae24eb6c254bdb9f1b91c8fa7c801d701ff8a5a6bbeb3c`. Preexisting HarfBuzz callback and `en` intern-cache gates avoided shared initialization; constructors, face/buffer extents, and flags-zero destruction were reviewed. The bounded launch hid all windows, zeroed only game audio output, sent no input, performed no GPU readback, preserved original saves/configuration, and left no game process. The 7,754-byte, 108-record capture has SHA-256 `a653391c124044bd34d3d3e9872b952ee8964b6a4af3c8a9ef460d7632e2df18`.

All selected maps were platform 0/encoding 3. Latin and Hani LTR retained nominal glyphs; Hani TTB substituted U+3042 from glyph 1461 to 65158 at all three sizes. Its font GSUB `vert`/`vrt2` single-substitution lookup 45 contains that exact replacement. U+0301 remained glyph 253 with zero vertical advance after shaping, despite a nonzero `vmtx` advance; its GDEF glyph class is mark, 3. Isolated surrogate units and U+FFFF produced glyph 0. These observed shaping changes remain explicit; nominal cmap/metrics are not substitutes for a shaping implementation. The [OpenType GSUB specification](https://learn.microsoft.com/en-us/typography/opentype/spec/gsub) defines single substitution and feature/lookup organization.

`PrepareVectorFontScale` recovers positive integral 72-dpi sizing from native `0x14039ee50` and fixed division `0x14039aa80`: scale is `((pixelSize * 64 * 65536) + unitsPerEm/2) / unitsPerEm`. `ScaleVectorGlyphAdvance26Dot6` preserves the fast-advance stage `0x1403a1080`, `(advanceUnits * scale + 32) >> 6`, before the HarfBuzz callback rounds with `(advance16 + 512) >> 10` horizontally or `(512 - advance16) >> 10` vertically. Vertical advance retains its negative shaping coordinate. This is an unhinted callback value before mark adjustment, positioning, or substitution, consistent with the [FreeType advance interface](https://freetype.org/freetype2/docs/reference/ft2-quick_advance.html). Invalid scale/range conversions fail explicitly instead of reproducing native signed overflow.

Three thousand unchanged native request-metrics/fast-scale/rounding paths matched all 9,000 words. The initialized owner capture matched all 216 measured advance words when converted from its actual shaped positions. A subsequent unchanged native post-shaping loop on those captured values matched all 540 advance/glyph/position words. First-party sfnt metrics and recovered scaling explain all ordinary advances; the three vertical mark adjustments and three glyph substitutions remain separate shaping observations. Retained fixed-point vectors, half-unit signed rounding, zero advance, invalid inputs and overflow checks passed strict compiler warnings and sanitizers. Multi-unit/context shaping, vertical origins, feature selection, glyph-outline hinting, software atlas rasterization, and native-versus-platform text pixels remain open.
