# Containing Looper phase admission

The original Display owns Pre/Post clocks in physical Looper groups `+0x80/+0x100`. Its native destructor `0x1404c2460` disposes dependent resources before finally unlinking Post and Pre. The exact containing Looper must remain alive and inactive throughout that teardown. Evidence is retained in the read-only Display hook audit, targeting `Files/STEINS.GATE.REBOOT/sgre_steam.exe`, SHA-256 `75a83a0e2a7e22055417ae0474b47be98418c4e42c695c548b558705c404b9d8`, explicit view `candidate:view:1:UEU`. No new native execution occurs here.

`LooperFrame::RequireIdleContainingPhase` observes its actual live serialized owner, iteration/wait flags, real worker-controller phase and all five physical group traversal/release phases. It admits registered clocks outside execution; unlike whole `CanClose`, it does not require the hooks to be removed first. `ParallelTaskSet::RequireIdleTraversal` reads only its existing traversal/release fields and invokes no task retirement callbacks. The containing Looper supplies thread/lifetime admission. No class layout changes or second callback registry are introduced.

This observation does not grant resource retirement or authenticate a completed frame. Pending writer work can exist while the controller is Idle; exact bound receivers and retained input borrows must independently fence a host pool. Real renderer/camera/root resource lifetimes and individual clock extraction also require their own checks. The admission does not drain, cancel, dispatch or manufacture readiness.

The bounded direct fixture exercises all eight iteration phases, all five standalone group traversals and all five actual release callbacks. Actual Post delivery outside Looper and a real worker callback reject containing admission. Foreign/closed owners reject. A deliberately failed authored root queues a genuine writer before throwing: the containing phase becomes inactive, while the writer correctly remains pending and nonquiescent until actual `RunFrame` joins it. The fixture confirms no unrelated `CanRelease` callback runs during phase observation. These are authored ownership checks, not a native shutdown, Display destructor or game-frame claim.

The next consumer is the concrete graphics frame/hook owner, paired with the actual frame host pool, backsurface and root draw. Existing whole-app and native fidelity acceptance remains open.
